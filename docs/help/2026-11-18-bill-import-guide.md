# 账单导入功能说明（普通投资者版）

> 状态：现行实现说明（2026-11-18），**以代码为准**。本文描述的是「上传券商对账单 → 进账本 → 影响资产/持仓/回合」这一整条链当前的行为，不记录历史方案。
>
> 相关文档：[账单解析与估值口径](../architecture/2026-10-29-bill-parsing-and-valuation-caliber.md)（历史设计，口径变更见其顶部说明）、[导入映射重构](../architecture/2026-11-13-import-mapping-refactor.md)（v2 列映射/类型确认）、[FIFO 与回合洞察](../architecture/2026-11-04-fifo-round-insights.md)、[API-Catalog v2](../architecture/v2/API-Catalog.md)（API-010~016、098~106）。

## 0. 先看结论

导入不是「把 Excel 原样塞进数据库」，而是分四步：

1. **认列**：这张表哪一列是日期、哪一列是代码、哪一列是金额；
2. **认类型**：每一行的「摘要」属于买入、卖出、分红还是资金划转；
3. **对账**：用账单里的「资金余额」列把流水串成一条不断裂的链；
4. **落账或隔离**：能确认的行写进账本，确认不了的行放进「隔离区」等你处理，**绝不猜**。

只有真正落账的行才会影响资产表、FIFO 持仓和回合；隔离行、被标记废弃的行、被撤销的批次都不会。

## 1. 第一步：列字段映射（这张表哪一列是什么）

### 1.1 系统认识的字段

字段目录定义在 `stock_contracts/import_fields.py::IMPORT_FIELD_CATALOG`，分为三层：

| 层 | 字段 | 说明 |
| --- | --- | --- |
| L1（必须有） | `trade_date` 成交日期 | 没有日期整张表无法导入 |
| L1（交易类必须有） | `security_code` 证券代码、`quantity` 数量、`price` 成交价格 | 买卖/申赎行需要；纯资金行（银证转账、利息）不要求 |
| L2（业务判断） | `side` 买卖标志、`amount` 发生金额、`summary` 摘要 | 决定方向、金额和分类 |
| L3（可选） | `security_name` 证券名称、`commission` 佣金、`stamp_tax` 印花税、`other_fee` 其他费、`cash_balance` 资金余额、`note` 备注、`account` 资金账号 | 有则更准，缺了也能导入（资金余额缺失会对账降级） |

v2 流程的别名表在 `FIELD_ALIASES`（如「成交日期/发生日期」「证券代码/代码」「发生金额/发生额」），legacy 自动识别用 `parsers/columns.py::COLUMN_ALIASES`。表头先做空白归一（去 BOM、全角空格、首尾空格），再按别名匹配。

### 1.2 金额列：毛额还是带符号净额

这是导入最容易出错的地方，代码里只有两种口径：

- **「发生金额 / 发生额」= 带符号净额**（已扣费用），直接采用，**不能再减一次佣金**；
- **「成交金额」= 毛额**，按方向换算成净现金流：
  - 买入：`-(成交金额 + 佣金 + 印花税 + 其他费)`；
  - 卖出：`+(成交金额 − 佣金 − 印花税 − 其他费)`；
  - 方向未知：金额记 0，并产生 `amount_unsigned_rows` 提示，由类型映射补方向。

实现见 `parsers/huatai.py::_net_amount_units` 与 `_gross_to_net_units`。

### 1.3 两套入口：legacy 与 v2

| 入口 | 列映射 | 适用 |
| --- | --- | --- |
| legacy（默认） | 按别名自动推断，映射结果随预览返回 | 已有券商格式，快 |
| v2（请求头 `X-Import-Flow: v2`） | 显式三阶段：API-098 保存列映射（`If-Match: mapping_version` 乐观锁）→ API-099 类型确认 → API-011 提交；API-100/101 模板、API-106 预览刷新 | 新券商、列名不标准、需要人工逐列确认 |

两条链路**共用同一个解析器和同一套业务语义**（`parse_bill`），v2 只是把「认列」和「认类型」拆成可人工确认的步骤，不会产生第二套金额/对账口径。

### 1.4 缺列、重名、认不出

- 必须字段缺失 → 预览直接报错（`IMPORT_MAPPING_INCOMPLETE` / `UNMAPPED_COLUMN` 隔离）；
- 表头重名或歧义 → 该列不自动采用，交给人工映射（v2）或按未映射处理；
- 无法识别的日期格式 → 整行 `INVALID_ROW` 隔离，不猜格式。

## 2. 第二步：账单类型映射（这一行算买还是算卖）

### 2.1 分类只有 11 种

`stock_contracts/enums.py::BillCategory`：

| 类别 | 含义 | 对下游的影响 |
| --- | --- | --- |
| `buy` | 买入（含基金申购确认） | 建仓、扣现金、进 FIFO |
| `sell` | 卖出（含基金赎回确认） | 平仓、加现金、结算回合 |
| `bonus` | 送转股 | 只改份额，不动现金 |
| `dividend` | 分红/红利 | 现金或份额增加，归入当日收益 |
| `rights` | 配股 | 份额与现金同时变化 |
| `interest` | 利息 | 计入收益 |
| `fee` | 费用 | 计入成本口径 |
| `transfer` | 资金划转（银证转入/转出） | 只改现金，不算盈亏 |
| `new_stock` | 新股/可转债中签缴款 | 特殊买入 |
| `broker_action` | 券商登记动作（申购中签、新股入账、证券清理、托管划转等） | **不扣款、不影响持仓、不计成本、不产生回合** |
| `other` | 其他 | 仅留痕 |

### 2.2 怎么匹配

`application/classify.py::match_rule`：

- 匹配方式：`exact`（全等）、`prefix`（前缀）、`contains`（包含）、`regex`（正则）；
- 按 `priority` **升序**取第一条命中的规则（数字越小越优先）；
- 系统默认规则在 `repositories/rules.py::SYSTEM_RULES`，例如：
  - `sys_sxt_out`：`[省心投]申购确认` → `transfer`（exact，priority 12）；
  - `sys_brk_*`：`申购中签 / 申购还款 / 新股入账 / 转托管 / 托管转出` → `broker_action`（priority 11）；
  - `sys_buy_stock` / `sys_sell_stock`：`证券买入 / 证券卖出` → `buy / sell`（priority 10）；
- 你在 v2「类型确认」里确认过的摘要会形成**用户类型记忆**，下次优先于系统规则；
- 匹配前摘要已做空白归一（折行、全角空格、NBSP、零宽字符全部删除），所以「[省心投]红\n利发放」和「[省心投]红利发放」是同一个键。

### 2.3 认不出来怎么办

- 摘要命中不了任何规则 → `UNKNOWN_SUMMARY` 隔离，**不会**按「其他」静默入库；
- 你主动把某类账单标记为「废弃」→ `BILL_TYPE_DISCARDED`，单独计数，不混进隔离数；
- 隔离区支持补规则/改类型后重跑分类（API-016），不需要重新上传文件。

## 3. 第三步：对账（余额链）

### 3.1 一句话

券商账单每一行都有一个「资金余额」，它等于上一行余额加减本行发生金额。把整份文件按这个公式串起来，只要中间断了一处，就说明账单缺行、列映射错了或金额口径错了——此时**宁可隔离，也不猜**。

### 3.2 具体规则（`application/chain.py`）

- 逐行核对：`上一行余额 + 本行带符号金额 == 本行资金余额`，容差 `EPS_AMT`；
- 多资金账户的账单**按资金账号拆成多条独立的链**，互不干扰；
- 没有资金余额的行：无法核对，接受，金额并入「待核对合计」，由下一条带余额的行整体验证；
- 第一次导入（库为空）：头部最多试 5 个候选锚点，取「后续能接受行数最多」的那个，并列取最早；
- 断链：从断行**连续隔离到链尾**（因为锚点已不可信），首条断行在 `raw` 里留下 `_chain_expected_units / _chain_actual_units / _chain_delta / _chain_counterpart`，导入结果页可直接看到「断在第几行、差多少钱、跟哪行比」；
- **不做任何零金额豁免**：任何带余额的行都参与核对。五金额全 0 的行在解析层就已经隔离，不会走到这里。

### 3.3 五种导入模式（`plan_chain`）

| 模式 | 什么时候 | 行为 |
| --- | --- | --- |
| `empty` | 账本里还没有这只账户的流水 | 整份导入（头部重试） |
| `covered` | 文件区间已被库内流水完全覆盖 | **全部跳过**，不隔离、不重复写 |
| `append` | 文件比库内更新 | 从库内最后一条余额接上，接缝不闭合直接报 `IMPORT_CHAIN_DISCONTINUOUS` |
| `backfill` | 补更早的历史 | 文件末行必须与库内首行闭合，否则整批报错 |
| `replace` | 文件区间落在库内（覆盖区段） | 以文件为准覆盖该区段，前后接缝仍需闭合 |

因此：**直接重传一份已经导入过的账单，什么都不会发生**（`covered`）。要让历史数据按新口径重新计算，必须先撤销（或删除）原批次再重导。

### 3.4 对不平时会补差，还是报错

- 文件内部某一段与上一行接不上 → 断链行进隔离区（`RECONCILIATION_BREAK`），已核对的前缀保留；
- 增量追加的**接缝**接不上、补历史接不上、覆盖区段前后接不上 → 整批失败（`IMPORT_CHAIN_DISCONTINUOUS`），提示断点日期与差额，不落半截数据；
- 对账发现的缺口可以写成 `side=missing`、`source=system` 的补差流水（一次补差后链闭合、重复调用幂等），批次返回 `filled_count / fills[]`，这类批次状态为 `degraded` 而不是 `blocked`。

## 4. 隔离：什么会被挡在账本外

隔离行只存在于「导入批次 → 隔离区」，不写 `ledger.trade`，因此**对资产、FIFO、回合、净值全部零影响**。原因码与界面文案来自 `stock_contracts/enums.py::QUARANTINE_REASON_LABELS`：

| 原因码 | 界面文案 | 触发条件 |
| --- | --- | --- |
| `INVALID_AMOUNT` | 金额字段无效或全为 0 | 佣金/印花税/其他费/发生金额/资金余额**五项全为 0**（不看摘要、不看份额） |
| `ZERO_AMOUNT_INFO` | 零金额通知行，无资金意义 | 金额 0、**资金余额列缺失**、摘要命中通知类关键词 |
| `UNKNOWN_SUMMARY` | 摘要无法识别，缺少业务分类 | 没有任何规则命中，且用户未确认类型 |
| `UNMAPPED_COLUMN` | 依赖的列未映射 | 分类需要的列没有映射 |
| `INVALID_ROW` | 字段无法解析（日期/数量/价格等） | 单元格解析失败 |
| `DUPLICATE_IN_FILE` | 文件内重复行 | 同一文件内去重键完全相同 |
| `RECONCILIATION_BREAK` | 资金余额链断裂，与上一行接不上 | 余额核对不一致 |
| `BILL_TYPE_DISCARDED` | 账单类型被标记为废弃 | 用户主动标记该类为噪音（单独计数） |

两个口径要点：

1. **全零就是隔离，没有任何摘要例外**。红利发放、非交易过户确认这类行如果金额和余额列都是 0，说明券商写的是占位值，不能当作真实余额；放进来会成为期末余额锚点，把总资产算错。
2. 隔离不是删除：`raw` 保留原始单元格（含份额、摘要），你可以核对后手工补录，或修正规则后重跑分类。

## 5. 导入之后：对资产表、FIFO、回合的影响

### 5.1 资产表（`review.asset_daily`，口径版本 2.4）

- 恒等式：`总资产 = 现金 + 持仓市值`；
- **货币基金是现金等价物**：份额按 1.0000 折算进现金，不参与 FIFO、不产生回合、不进「持仓市值」（口径 2.3 起）；
- 非货基持仓：A 股/场内基金优先用行情价，缺行情时按含费成本兜底；债券/伪代码按成本估值；
- 只有**落账**的流水参与计算。隔离行、废弃行、被撤销批次的行都不参与；
- 超卖日（持仓不足以卖出）不会被编成负数：当日资产标记 `degraded`，你可通过「超卖修订」补正，修完自动重建；
- 资产口径版本（`ASSET_DEFINITION_VERSION`）升级时会触发**全量重建**，因为旧资产行是按旧公式算的。

### 5.2 FIFO 持仓与成本（`stock_core/fifo/engine.py`）

- 每笔买入形成一批持仓批次，卖出按「先买先卖」消耗批次，算出已实现盈亏与剩余成本；
- 排序键是 `（成交日期, 文件行号, 记录 id）`，所以**同一毫秒写入的多行也能稳定复放**，导入顺序不会打乱 FIFO；
- 送转、配股会调整批次份额/成本；分红按除权日归入对应持仓的收益；
- `broker_action`、`transfer` 不参与 FIFO；货基不进 FIFO（见 5.1）；
- 卖出数量超过持仓 → 超卖，批次标记 `data_error`，持仓按 0 截断，**绝不出现负持仓**；这笔数据需要人工修订。

### 5.3 回合

- 回合是「一只标的一次完整买入→卖出」的统计单元，由已落账流水重建（`rebuild_rounds`），不是导入时直接写入的；
- 导入/撤销/超卖修订改变流水后，会触发回合重建；**隔离行不产生回合**；
- 分类错误（例如把申购确认误判成买入）会直接改变持仓和回合，所以导入前要确认类型映射。

### 5.4 净值与指标

- 净值、TWR、18 项指标都读资产表和回合结果，不使用另一套口径；
- 出入金（`transfer`）在收益计算中作为外部现金流剔除，不当作盈亏；
- 数据 `degraded` 时指标会降级标注，而不是给出一个看似正常的错误值。

### 5.5 撤销导入

- 撤销批次会软删该批次所有明细（含 `source=system` 的补差行），并触发资产/回合/净值重建，数据回到导入前；
- 撤销后重新上传同一文件，才会重新走解析、对账、隔离；这正是「历史数据按新口径重算」的唯一正确路径。

## 6. 三个真实场景

### 6.1 红利发放为什么没进账本

2026-10-27 批次最后一条是 940018 红利发放：金额 0、份额 407.6、资金余额列 0，而上一笔申购确认后余额是 101.15。五金额全 0 → 解析层直接 `INVALID_AMOUNT` 隔离，界面文案「金额字段无效或全为 0」。这样做避免了把占位的 0.00 当成期末余额锚点（否则总资产会凭空少 101.15 元）。需要这 4.08 元红利留痕时，从隔离区人工补录。

### 6.2 为什么重传同一份账单什么都没发生

因为该区间已被库内流水覆盖，`plan_chain` 判定 `covered`：全部跳过、不隔离、不重复写。要修正历史数据，必须先撤销原批次再重导。

### 6.3 余额链断了怎么办

先看导入结果页的差额提示（`_chain_delta`、`_chain_counterpart`）：常见原因是漏传了中间某段账单、金额列被映射成毛额（或带符号列被当成毛额二次扣费）、资金余额列映射错。修正后重新预览——断点之后的行会整段进隔离区，不会带着错误余额继续入账。
