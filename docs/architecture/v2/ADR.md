## ADR-0013 云上单机多容器 + 模块化单体（两个部署单元）

**状态**：采纳 ｜ 2026-10-19 ｜ **取代 ADR-0001**
**背景**：PRD-v2 要求"第一版即多用户 + 云主机部署"。v1 的单进程 + SQLite 无法支撑并发用户与服务级可用性；但需求方未要求 K8s/多活，且团队为单人维护。
**决策**：部署形态为**单云主机 + Docker Compose**（nginx / api×N / worker×M / postgres / migrate）。代码为**模块化单体**，产出**两个部署单元**（`api` 与 `worker`），同镜像不同入口，共享 domain/application。不拆微服务、不上 K8s。
**理由**：① 满足多用户与云部署；② 运维复杂度与单人维护预算匹配；③ api 无状态可水平扩副本，worker 可独立扩；④ 迁移路径清晰（后续可平滑上多机/托管 PG/K8s，而无需改代码分层）。
**后果**：
- 正面：部署简单、调试集中、事务一致、成本低。
- 负面：**主机级故障仍中断服务**（单故障域）；PG 单点；扩展上限受单机资源约束。
- 缓解：api ≥2 副本消除进程级单点；PITR + 重建 SOP 应对主机故障；容量与扩容决策表见 Reliability §9；重新评估触发条件：日活 >200 / 需要 99.95% / 多地域访问。
**被否方案**：K8s（运维过重）；微服务（分布式事务与跨服务鉴权成本远超收益）；Serverless + 托管 PG（DB 连接与长任务不匹配）。
**关联需求**：FR-L1、NFR-10、NFR-13。

## ADR-0014 PostgreSQL 单库多租户（user_id + RLS）

**状态**：采纳 ｜ 2026-10-19
**背景**：100 用户量级、单租户数据量小（≤5 万行）。需要隔离，但不值得为每用户建库/建 schema。
**决策**：**共享库 + 共享 schema + `user_id` 列**，所有租户表启用 **Row Level Security**；每请求事务内 `SET LOCAL app.user_id`；应用连接使用**非 owner 角色**（避免绕过 RLS）。
**理由**：① 运维最简、迁移一次到位；② 查询天然跨租户聚合（系统统计）；③ RLS 提供结构性隔离，不依赖开发者自觉；④ 后续升级团队租户只需引入 `tenant_id`（Extensibility §4 给了五步迁移）。
**后果**：
- 正面：简单、成本低、隔离有第二道防线。
- 负面：RLS 策略需逐表维护；连接池串号是真实风险（前请求变量残留）；超级用户/owner 连接会绕过 RLS。
- 缓解：`SET LOCAL` 在事务内 + 连接归还钩子强制 `RESET`；应用角色无 `BYPASSRLS`；专门集成测试验证"跨租户直连读为 0 行"。
**被否方案**：schema-per-tenant（100 个 schema 的迁移与连接管理成本高）；database-per-tenant（更重）；仅应用层过滤（单点失误即泄漏）。
**关联需求**：FR-L2、NFR-6、NFR-1。

## ADR-0015 任务队列用 PostgreSQL `SKIP LOCKED`

**状态**：采纳 ｜ 2026-10-19 ｜ 取代 ADR-0007 的"进程内事件总线"部分
**背景**：导入/重算/报告/导出都是长任务，必须异步且可靠、可重试、可取消。需求方偏好技术栈未提 Redis，且 C5 约束不引入额外中间件。
**决策**：`platform.job` 表 + `FOR UPDATE SKIP LOCKED` 出队 + 租约/心跳 + 指数退避重试 + 幂等键 + 部分唯一索引实现单飞。事件用同库 outbox 表。
**理由**：① 少一个必须运维的有状态组件（对单人运维是决定性优势）；② 任务与业务数据同库 → 可在同一事务内"写结果 + 完成标记"，天然一致；③ 吞吐（≥100 任务/分钟）远超本场景需求。
**后果**：
- 正面：零新增运维、事务一致、可查询可审计（任务本身就是数据）。
- 负面：轮询带来空转与延迟（秒级）；PG 承担队列负载；高并发时锁争用。
- 缓解：`LISTEN/NOTIFY` 唤醒 + 短暂轮询兜底；出队索引 `(status, available_at)`；worker 数量受 `max_connections` 约束。
**被否方案**：Redis/Celery（多一个组件 + 结果一致性弱）；Kafka（明显过重）；进程内线程池（崩溃丢任务，且与多副本冲突）。
**关联需求**：FR-L3、FR-R2、FR-D2、NFR-5、NFR-13。

## ADR-0016 前后端分离：React SPA + REST，nginx 同源

**状态**：采纳 ｜ 2026-10-19 ｜ **取代 ADR-0006**
**背景**：需求方明确偏好"前后端分离（前端 React、后端 Python）、重后轻前"，与 v1 的 SSR+HTMX 相反。
**决策**：前端为 **React 18 + TS 的 SPA**（Vite 构建静态产物），由 nginx 提供；后端提供 REST API。**前后端同源部署**（nginx 把 `/api` 反代到 api 服务），不使用跨域 CORS。
**理由**：① 遵循需求方技术形态；② 同源让 refresh token 可用 httpOnly cookie，规避 CORS + 三方 Cookie 的复杂度与安全坑；③ 静态资源与 API 同域，减少运维面；④ SPA 与 API 可独立部署（同一主机不同产物）。
**后果**：
- 正面：分工清晰、前端迭代不需改后端渲染、缓存策略简单。
- 负面：首屏依赖 JS；需处理认证刷新与版本兼容窗口；前端测试成本上升。
- 缓解：路由级代码分割 + 关键数据并行拉取；401 静默刷新一次；N-1 兼容承诺（Architecture-v2 §12.4）。
**被否方案**：SSR/Next.js（需求未要求 SEO，增加部署与编译复杂度）；纯 CORS 跨域（Cookie/CORS 配置风险）；继续 HTMX（与需求方偏好冲突）。
**关联需求**：FR-D1、FR-D3、NFR-8。

## ADR-0017 OpenAPI 单源 + 生成式 SDK + 验收 100% 端点

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD-v2 把"API 可验收"列为首要目标（G3、FR-A2）。前后端分离后，契约是最容易漂移的边界。
**决策**：以 FastAPI 生成的 **OpenAPI 3.1** 为唯一契约源 → 快照提交 `openapi/openapi.json` → 前端 SDK 由契约生成（禁止手写请求/响应类型）→ CI 强制：示例/错误码/`operationId` 完整性、快照 diff、**验收套件覆盖 100% 端点**。
**理由**：① 契约漂移是前后端分离的头号故障源，必须机器校验而非靠约定；② 生成式 SDK 让前端"不可能写错字段名"；③ 端点覆盖率可度量，使"完成"可判定（这正是需求方要的"可验收"）。
**后果**：
- 正面：验收客观、漂移阻断、SDK 与文档自动同步、可对第三方开放。
- 负面：契约变更流程变重（breaking 需升版本）；生成代码需要构建步骤。
- 缓解：只对"破坏性"变更加流程；生成代码纳入 CI 缓存；`Deprecation`/`Sunset` 头给消费方迁移期。
**被否方案**：手写 SDK（必然漂移）；GraphQL（需求方偏好 REST，且验收更复杂）；契约优先但人工维护 YAML（易与实现脱节）。
**关联需求**：FR-A2、NFR-7、NFR-8、NFR-11。

## ADR-0018 PG 事务分级 + WAL 归档 PITR

**状态**：采纳 ｜ 2026-10-19 ｜ **取代 ADR-0008**（其精神保留：不可重建的数据必须更强耐久性）
**背景**：v1 用"事实 FULL / 派生 NORMAL"在 SQLite 上分级；v2 迁到 PG 后需要服务级 RPO ≤5min、RTO ≤30min。
**决策**：PG `synchronous_commit=on`（默认，保证已提交事务不丢）+ `wal_level=replica` + `archive_mode=on` 持续归档 WAL 到备份位置；每日全量备份（`pg_dump` 或 `pg_basebackup`）+ checksum + 关键聚合校验；恢复以 **PITR** 为主路径，季度演练。
**理由**：① 服务级 RPO 只能靠 WAL 归档；② 每日全量单独不足以满足 5min；③ PITR 能恢复到任意时间点，比"最近一次备份"更符合事故处置需求。
**后果**：
- 正面：RPO ≤5min、可审计、可演练。
- 负面：归档占用存储与带宽；恢复流程需演练否则等于没有。
- 缓解：归档保留策略与生命周期；`make restore-drill` 脚本化；恢复后自动跑关键 API 验收子集与 `doctor`。
**被否方案**：仅每日全量（RPO=24h，不满足）；逻辑复制热备（首版可用但不解决 PITR）；云托管自动备份（需求方自管云主机）。
**关联需求**：NFR-13、FR-L7、NFR-4。

## ADR-0019 长任务异步化：202 + job + SSE

**状态**：采纳 ｜ 2026-10-19
**背景**：导入 5000 行、全量重算、报告生成、导出都超过可接受的同步等待；而 NFR-10 要求读 p95 ≤300ms。
**决策**：所有长任务返回 `202 Accepted` + `Location: /api/v1/jobs/{id}`；进度通过轮询与 `GET /jobs/{id}/events`（SSE，支持 `Last-Event-ID` 续传）；任务可取消、可续跑、有最终结果引用。
**理由**：① 保住 API 延迟预算；② 任务状态本身是可验收对象（可断言终态与结果）；③ SSE 比 WebSocket 简单且足够单向。
**后果**：
- 正面：API 快速返回、任务可观测、前端体验可控。
- 负面：调用方需处理"提交-轮询"两段式；状态机变复杂。
- 缓解：SDK 提供 `waitUntilDone(jobId)` 辅助方法；契约中固定状态机与错误码；SSE 断线自动降级为轮询。
**被否方案**：同步阻塞（超时与雪崩风险）；WebSocket（双向能力用不上）；仅轮询无 SSE（可接受但不佳，作为降级路径保留）。
**关联需求**：FR-L3、FR-R2、FR-D2、FR-L7、NFR-10。

## ADR-0020 多租户双层隔离（仓储过滤 + RLS）

**状态**：采纳 ｜ 2026-10-19
**背景**：多租户最严重的失败模式是**跨租户数据泄漏**，且必须测试证明其不发生（G4、NFR-6）。
**决策**：**双层**隔离——① 应用层：仓储方法强制注入 `user_id`（由 `TenantContext` 提供，不可由请求参数覆盖）；② 数据库层：RLS 策略 + 每事务 `SET LOCAL app.user_id`，应用连接使用非 owner 非 `BYPASSRLS` 角色。跨租户资源一律返回 **404**（不泄露存在性）。
**理由**：① 单层防御的失败概率不可接受；② RLS 能兜住"新增查询忘了加条件"这类真实事故；③ 404 语义避免信息泄露（枚举探测）。
**后果**：
- 正面：结构性防呆、可审计、可测试（直连 SQL 断言越权读 0 行）。
- 负面：每个租户表都要策略；连接池变量残留风险；调试时可能"看不到数据"。
- 缓解：策略由迁移统一生成；连接归还强制 `RESET`；提供管理员只读系统视图（无明细）；越权负向用例 100% 受保护端点（Testing §4）。
**被否方案**：仅应用层过滤（单点失误即泄漏）；仅 RLS（SQL 报错对开发者不友好，且性能调试困难）；每用户独立库（运维不可行）。
**关联需求**：G4、FR-L2、NFR-6、NFR-1。

## ADR-0021 前端零口径（生成式 SDK + AST 断言）

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD-v2 要求"重后轻前""前端不得实现业务口径"。但赶工期时最容易发生的就是"前端顺手算个差值"。
**决策**：前端只消费 API 返回的 `value / conclusion / method / drilldown / status`；① SDK 由契约生成（字段不可能写错）；② ESLint 规则 + AST 断言测试禁止在 `frontend/` 出现指标计算与结论文案拼接；③ 后端在 `status != ok` 时不返回 `value`，使"前端无法算出错误数字"。
**理由**：① 口径双实现必然漂移，且漂移后无人能判断哪个对；② 结构性禁止比评审提醒可靠；③ 与 v1 的"结构化产物 + 渲染层分离"一致。
**后果**：
- 正面：口径单一实现、前后端一致、可复用给第三方客户端。
- 负面：前端需要更多"纯展示"组件；少量格式化逻辑（金额展示）仍需允许（白名单）。
**缓解**：白名单仅允许"展示格式化"（`lib/format`），并要求单测；AST 断言纳入 CI 硬门禁。
**被否方案**：前端算派生值（漂移风险）；后端返回已渲染 HTML（违背前后端分离）。
**关联需求**：FR-D1、FR-D3、NFR-8、G7。

## ADR-0022 LLM 旁路 + 金额后端填充 + 出站守卫

**状态**：采纳（v1 ADR-0012 的强化版）｜ 2026-10-19
**背景**：v1 已定"LLM 只组织语言、金额本地填充"，成功同时满足隐私与可用性。v2 变为多用户服务后，LLM 风险面扩大（多租户信息混入、成本、配额、合规）。
**决策**：保持旁路架构：后端 `ToolGateway` 取数 → `ResponseComposer` 模板填充数值与 `citations` → `EgressGuard` 硬断言出站 payload 不含金额/账号/邮箱/股东代码 → 仅把指标名/比例/分位/样本量交给 LLM。LLM 不可用或未配置时返回模板化答案；服务端统一 key + 用户级开关。
**理由**：① 隐私事故零容忍；② LLM 故障不应影响正确性，只影响措辞；③ 成本与配额集中在服务端可控。
**后果**：
- 正面：无泄漏出站、断网可答、成本可控、可审计（`llm_call.redaction_applied`）。
- 负面：措辞灵活度受限；模板维护成本。
- 缓解：固定问题按钮覆盖高频场景；自由输入走模板组合；出站守卫有专项测试（构造含金额上下文断言被拦截）。
**被否方案**：LLM 直连数据库（越权 + 泄漏）；把金额传远端做"本地脱敏"（已经出站即失败）；完全不做 LLM（不满足 FR-D7）。
**关联需求**：FR-D7、NFR-1、NFR-14、G8。

## ADR-0023 软删用于业务追溯，注销物理删除

**状态**：采纳 ｜ 2026-10-19
**背景**：v1 规定"删除历史永不物理清除"，但 v2 面向多用户服务，用户需要**数据删除权**（PRD §4.4）；两者直接冲突。
**决策**：区分两类删除——① **业务软删**（用户删一条流水、撤销批次）：`deleted_at` 标记，可恢复、可追溯、不参与下游；② **账号注销**：物理删除该用户全部业务数据（级联 + 审计留痕，不含明细内容）。
**理由**：① 合规优先于"永不删除"的技术洁癖；② 但业务回溯能力对复盘产品是核心价值，不能被注销需求连带削弱；③ 显式区分可避免实现时含糊。
**后果**：
- 正面：合规可满足；业务审计仍完整；删除路径有测试。
- 负面：物理删除是危险操作，需要二次确认与限流。
- 缓解：注销需重新认证 + 二次确认 + 审计；删除后提供"导出后再注销"引导；恢复窗口内可联系管理员。
**被否方案**：全部硬删（丢失追溯能力，与 FR-L4 冲突）；全部软删（不满足删除权）。
**关联需求**：FR-L4、FR-L7、NFR-1、NFR-5。

## ADR-0024 分层差异化覆盖 + 契约/越权硬门禁

**状态**：采纳（ADR-0010 的 v2 版本，原决策延续）｜ 2026-10-19
**背景**：v1 已确立"覆盖率≠正确性"。v2 新增两类高危缺陷：**越权泄漏**与**契约漂移**，而覆盖率对这两类基本无感。
**决策**：保留分层差异化覆盖率（core 100/100；各层递减；整体仅告警；diff ≥95% 硬），并**新增两道硬门禁**：① **OpenAPI 端点验收覆盖 100%**；② **越权负向用例覆盖 100% 受保护端点**。并列四道"覆盖率抓不到"的门：golden/oracle 对拍、边界矩阵、变异测试、架构约束（含前端零口径与 RLS 直连验证）。
**理由**：① 门禁必须对齐真实风险，而不是对齐一个漂亮的百分比；② 越权与契约是 v2 的新增风险面，必须可度量；③ 三道硬门禁（端点、越权、diff）足以防止"新代码裸奔"。
**后果**：
- 正面：风险与投入对齐；验收可判定；架构腐化有测试拦截。
- 负面：CI 时间增加；需要维护"端点清单 ↔ 用例"映射。
- 缓解：fast/full/nightly 分段；端点清单由契约自动生成，用例缺失即列在报告中。
**被否方案**：全局 100% 覆盖（浪费且鼓励无意义断言）；只靠人工验收（不可持续）。
**关联需求**：NFR-7、FR-A2、NFR-6。

## ADR-0025 行情估值口径与缓存策略（不复权 + 并集覆盖）

**状态**：采纳 ｜ 2026-10-23 ｜ 依据：设计 [2026-10-22-live-market-data-source.md](../2026-10-22-live-market-data-source.md) v2 与评审裁定 D1–D4
**背景**：真实账单（2021-10，000651/601688）请求 `GET /nav` 时因 replay 行情 fixture 覆盖不足被判 blocked，需要接入 akshare 真实行情。行情接入同时牵动三类决策：估值用哪种复权口径、缓存如何失效、外部依赖如何隔离；且与 PRD NFR-2（后复权 + as-of 因子快照 + 涨跌停/因子跳变校验）存在阶段性偏离，必须显式记录。
**决策**：
1. **估值口径：不复权（D1）**。v1 只落不复权日线（akshare `adjust=""`），`market.daily_bar.adjust` 恒为 `''`，`capabilities.supports_adjusted=False`；`MARKET_LIVE_ADJUST` 只接受 `""`，显式拒绝 `qfq/hfq` 误配。
2. **缓存：区间并集 + 尾部刷新 + TTL（D3）**。新建 `market` schema 公共缓存两表（`daily_bar` / `pull_range`，无 RLS、可再生）。覆盖判定用 `pull_range` 区间并集：已结束区间以 `requested_end` 为覆盖上界（非交易日不重拉），含未来/当月区间只用 `data_end` 覆盖且尾部 `MARKET_LIVE_TAIL_REFETCH_DAYS`（默认 5 天）恒为缺口；正缓存 TTL 30 天、负缓存（区间无行情）短 TTL 1 天；`daily_bar` 按 `(symbol, adjust, trade_date)` 幂等 upsert，`pull_range` 按 `ON CONFLICT` 覆盖并落 `source/checksum/bar_count/pulled_at` 留痕（NFR-2 最小来源留痕）。
3. **契约与依赖（D2）**：不新增错误码，保持 degraded `blocked` 200；失败类别经 `ApiError.metadata["market_failure"]` 传给 nav，`/nav` 仅新增可选响应字段 `blocked_reason`（非破坏）。akshare 走 optional extra `live`（`uv sync --extra live`），启动期 `find_spec` fail-fast；上游并发上限 2 + 有上限重试 + `to_thread` 隔离。
4. **NFR-2 分阶段偏离**：hfq + 复权因子 + `factor_version` 失效 + as-of 因子快照 + 涨跌停/因子跳变校验留到后续期次；v1 不做上市日期校验（空结果统一 `no_data` + 负缓存短 TTL）。
5. **实现位置偏离**：实现在 `stock_platform/market_live.py`（行情是跨用户公共基础设施，放 platform 语义最准），与 Extensibility EP-2 规划的 `review/infra/marketdata/` 不同；ledger 只保留装配工厂并透传 `session_factory`，不直接读写缓存表。
**理由**：① NAV 公式 `现金 + Σ(数量 × 收盘价)` 需要**真实市价**；qfq 是相对最新价缩放的历史序列，会让总资产绝对值、MWR、多标的组合权重同时失真，且可能为负。② 账单中股息/红利已作为 `category=dividend` 现金流入账，qfq 又把分红折入价格，除权日会**重复计入**。③ akshare 官方确认 qfq 历史价格时变，与永久缓存不相容。④ 区间并集 + 尾部刷新 + TTL 同时满足「连续月份增量拉取」「当月不漏新交易日」「上游修正可自愈」，且无需引入增量列/分区或额外中间件。
**后果**：
- 正面：历史账单可出数（2021-10 的 000651/601688）；重复查询走缓存、连续月份只拉缺口；不复权口径与账单现金流自洽、可确定性复算；缓存可随时重建，不背备份责任。
- 负面：与 PRD NFR-2 的「后复权/as-of 因子」要求暂时偏离；首次冷缓存打破 NFR-10 读 p95 ≤300ms；单源无灾备、无熔断；缓存表无 RLS（依赖「公共数据 + 不开放 HTTP 写路径」控制）。
- 缓解：hfq/因子版本后续期次补齐；NAV 异步化把取数移出请求事务；补灾备源与统一出站治理；缓存命中优先 + 并发 2 + 重试克制；downgrade 直接 drop `market` schema。
**被否方案**：qfq 前复权估值（时变 + 股息重复计入 + 可为负）；hfq 估值（v1 无因子快照，无法保证 PIT 正确性，留后续期次）；无 TTL 的永久缓存（上游修正与新股上市/停牌恢复无法自愈）；每次请求全量重拉（东财按并发封 IP，延迟不可接受）；新增 `MARKET_DATA_UNAVAILABLE` 错误码或 503（`/nav` 消费方吞 `ApiError`，503 是死码）；Redis/独立缓存服务（多一个有状态组件，与「不引入额外中间件」约束冲突）；行情放 `review` schema（跨用户公共数据不属于复盘租户域，且 RLS 语义不符）。
**关联需求**：FR-R1、NFR-2、NFR-9、NFR-10；见 Reliability §7/§8 的降级矩阵与出站治理。
