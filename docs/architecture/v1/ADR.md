## ADR-0001 单进程 + SQLite 单文件作为默认形态

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD-v1 §4.3 硬约束要求"零数据库安装、双击可用、有页面"。目标用户是非程序员个人投资者，数据量 ≤5 万行流水、DB <300MB。同时 v1.0 曾设计"两服务 + PostgreSQL 同实例分库 + 变更流 + 水位线增量同步"。
**决策**：交付形态为**单进程应用 + SQLite 单文件（WAL）+ 表前缀逻辑分库**；PostgreSQL 降级为未来云端可选 profile。v1.0 的变更流/水位线/镜像/墓碑不作为产品需求。
**理由**：
1. SQLite 在 5 万行量级有 1~2 个数量级余量，性能不是瓶颈。
2. 多进程/多库的真实收益（故障隔离、独立扩缩容）在单用户场景为零，而代价是用户装不起来。
3. 单文件使"备份 = 复制文件""迁移 = 拷目录"成立，直接满足 FR-L7 数据主权。
4. 消除水位线同步后，FR-R1 从"分布式一致性问题"降级为"同库只读查询"，删除一整类 bug。
**后果**：
- 正面：零安装、部署面最小、备份迁移简单、调试只需一个进程。
- 负面：必须自建单写者串行化、作业续跑、启动自愈；无法水平扩展。
- 缓解：单写者队列 + WAL + 可续跑作业（Reliability §3/§5）；明确换库触发条件（Architecture §14.3）。
**被否方案**：
- 微服务 + PG + 多容器：违反 C1/C2，用户无法安装。
- 仅 PostgreSQL 单进程：仍需用户装数据库服务。
- DuckDB：分析快但并发写与事务语义不适合"边导入边查询"。
**关联需求**：FR-L1、FR-L7、FR-R1、NFR-6、NFR-8。

## ADR-0002 六边形分层 + 消费方定义端口

**状态**：采纳 ｜ 2026-10-19
**背景**：核心风险是口径错误，而口径代码若与 ORM/HTTP 纠缠，就无法 100% 覆盖、无法属性测试、无法脱离数据库复算。PRD-v1 NFR-7 要求"关键路径 golden fixture"。
**决策**：严格分层 `presentation → application → domain ← infrastructure`；**端口由消费方（domain/application）定义**，infrastructure 实现；`packages/core` 为无 I/O 的纯计算内核；用 import-linter 强制契约。
**理由**：
1. 纯函数才能做 100% 行/分支覆盖与变异测试（ADR-0010 的前提）。
2. 消费方定义端口 = 依赖倒置，计算层不知道数据库存在，可用内存替身测试。
3. 架构约束可测试化，防止半年后腐化成"什么都 import"。
**后果**：
- 正面：core 可脱离 DB 测试；换存储/换数据源不影响计算；口径集中可审计。
- 负面：需要写映射层（ORM ↔ 值对象），有样板代码；开发者需自律。
- 缓解：`contracts` 包统一 DTO；Repository 提供批量接口；样例代码作为模板。
**被否方案**：
- 传统三层（Controller-Service-DAO）直接传 ORM 实体：口径函数被 I/O 污染，无法纯测。
- Django 风格 active record：领域对象绑 DB，不可属性测试。
**关联需求**：NFR-5、NFR-7、NFR-8、FR-R2/R3/R5。

## ADR-0003 标度整数表示金融数值

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD 附录 A 要求金额容差 0.01 元、收益率容差 1bp；涉及 FIFO 成本分摊、份额法净值、TWR 连乘、bootstrap 重抽样。float 会引入不可解释的尾差；SQL `DECIMAL` 在不同方言/驱动下行为不一致。
**决策**：全部金额/价格/数量/比率使用**标度整数**（金额 ×100 分、价格 ×1e6、数量 ×1e4、比率 ×1e8），在 `core/values` 封装为不变量类型（`Money`、`Qty`、`Price`、`Ratio`）；只在边界（UI 展示、导出、LLM 文案）转换为 Decimal/字符串。
**理由**：
1. 精确十进制、可确定性复算（同一输入必得同一输出）。
2. 跨库可移植（INTEGER 到处一致），避免 Numeric 方言差异。
3. 比 Decimal 快 1~2 个数量级，满足 60s 全量重算预算。
**后果**：
- 正面：容差比较稳定、golden 复算无尾差、性能好。
- 负面：需统一标度约定，除法要显式定义舍入（银行家舍入 + 显式精度），开发者易错。
- 缓解：`Ratio.div()` 强制要求传入 `RoundingPolicy`；容差比较统一用 `assert_money_close(a,b,eps=1)` 助手；CI 禁止 float 出现在 `core`（AST 检查）。
**被否方案**：
- `float`：容差 0.01 元下不可靠，且无法复现。
- `decimal.Decimal`：正确但慢，且与 SQL 交互需反复转换。
**关联需求**：FR-R2、FR-R3、FR-R5、NFR-5、NFR-10。

## ADR-0004 指标注册表 + 框架代算统计量与状态

**状态**：采纳 ｜ 2026-10-19
**背景**：FR-R8（N<10 不出结论、附 CI）、FR-D3（三段式解释）、G2（可追溯）、NFR-11（口径版本化）是**横切**于全部指标的。若每个指标各自实现，必然出现不一致（v1.0 评审已暴露"有的指标有 N、有的没有"）。
**决策**：所有指标以 `MetricDef` **声明式注册**，`n / CI / assumptions / inputs_hash / sample_status / status` 由框架统一计算；指标实现者只提供 `compute`、`explain`、`drilldown`、`sample_policy`。执行按 `depends_on` 拓扑排序。
**理由**：
1. 横切需求集中实现一次，天然一致。
2. 新增指标只需 1 个定义文件（Extensibility EP-1），满足"高扩展性"判据。
3. 口径版本化与失效传播可机械化（`definition_version` + `inputs_hash`）。
4. 三段式文案可从元数据自动生成，避免"有的数字能解释、有的不能"。
**后果**：
- 正面：一致性、可追溯、可扩展、可审计。
- 负面：注册表字段若设计过宽会变成"半个 DSL"，产生抽象税。
- 缓解：字段冻结在 v1 最小集；新增字段必须提 ADR；拒绝通用表达式引擎（见 Extensibility 反扩展清单）。
**被否方案**：
- 各指标自算：一致性无法保证。
- 通用表达式 DSL（JSON 公式引擎）：调试困难、确定性难保证、性能不可控。
- 数据驱动 SQL 指标：无法表达 bootstrap/CI 与跨行依赖。
**关联需求**：FR-R4~R8、FR-D3、G2、NFR-11。

## ADR-0005 结构化产物与渲染层分离

**状态**：采纳 ｜ 2026-10-19
**背景**：Review §3 R-C3 的裁决——投资者要求"我要一句人话，不要 JSON"，金融评审要求"结构化 meta 不能砍"。
**决策**：DB 与 API 层一律存**结构化结果**（`value_json` + `n` + `ci` + `assumptions` + `data_as_of`）；**人话由渲染层按 `explain` 模板生成**。禁止把结论性文案写入数据库。
**理由**：
1. 结构化是追溯、复算、趋势、跨期对比的唯一可靠基础。
2. 文案可随版本改进而不影响数据；同一结果可渲染到页面、报告、对话三个出口。
3. 避免"文案与数字脱钩"（改了数字忘了改文案）。
**后果**：
- 正面：三出口一致；文案可回归测试（快照）；支持未来多语言/多措辞。
- 负面：渲染层需要文案质量保障；模板与指标定义需同步演进。
- 缓解：文案快照测试 + 术语扫描测试（禁止裸术语）+ 合规文案白名单。
**被否方案**：把 `conclusion_text` 存进 `metric_result`——数字一改文案就撒谎。
**关联需求**：FR-D1、FR-D2、FR-D3、G2。

## ADR-0006 SSR + HTMX + 本地静态资产

**状态**：采纳 ｜ 2026-10-19
**背景**：需要"有页面"（FR-D1）但明确"不做重前端工程化"（PRD §7），且必须离线可用（C3）、零安装（C2）。
**决策**：Jinja2 服务端渲染 + HTMX 做局部刷新 + SSE 做长任务进度；ECharts/HTMX/CSS **全部 vendored 到仓库**，不使用 CDN，不引入 node 构建链。
**理由**：
1. 无构建步骤 = 零安装约束成立；用户不需要 node/pnpm。
2. 离线可用 = 本地资产；报告可自包含。
3. 单语言（Python）降低单人维护成本。
4. 本产品交互复杂度低（卡片、表格、图表、下钻），HTMX 足够。
**后果**：
- 正面：简单、离线、快、可测试（快照）。
- 负面：复杂交互（拖拽、富文本编辑）实现笨拙；前端状态管理能力弱。
- 缓解：明确不做复杂交互；下钻用抽屉式局部刷新；图表用 JSON 端点 + ECharts。
**被否方案**：SPA（React/Vue）+ 构建链——违反零安装与离线约束，且单人维护两套栈。
**关联需求**：FR-D1、FR-D2、FR-D3、NFR-12、C2、C3。

## ADR-0007 事件走 outbox 而非消息中间件

**状态**：采纳 ｜ 2026-10-19
**背景**：需要"导入完成→触发重算""异常→生成提醒""报告生成→推送"等松耦合扩展点（FR-D6、FR-D8 的 P2 预留），但不能引入 Redis/Kafka（违反 C1）。
**决策**：进程内 `EventBus` + `sys_outbox_event` 表实现 **at-least-once** 投递；消费者幂等；事件 schema 只允许新增可选字段。
**理由**：
1. 满足"以后加提醒/推送不改核心"的扩展需求。
2. 零外部依赖，且事件有持久化记录，崩溃后可重放。
3. 比直接函数调用多一层解耦，但成本极低（一张表 + 一个循环）。
**后果**：
- 正面：扩展点清晰；崩溃不丢事件；可回放调试。
- 负面：最终一致（页面可能短暂滞后）；需处理重复投递。
- 缓解：消费者按 `event_id` 幂等；关键路径（导入结果页）用同步返回，不依赖事件。
**被否方案**：Kafka/RabbitMQ/Redis Streams（运维成本为零收益）；纯进程内内存事件（崩溃丢事件）。
**关联需求**：FR-D6、FR-D8、FR-R1、NFR-5。

## ADR-0008 事实数据强持久化、派生数据弱持久化

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD 要求"已提交导入 RPO=0"（数据不可重建），而指标/净值等派生数据**可由事实数据全量重建**（NFR-5）。全库 `synchronous=FULL` 会显著拖慢批量重算。
**决策**：按数据性质分级——`ledger_*` 事实表写入使用 `synchronous=FULL`；`review_*` 派生表重建使用 `synchronous=NORMAL`（进程崩溃安全，仅 OS 崩溃可能丢最后若干派生写，但可重算）。
**理由**：耐久性成本应只花在不可重建的数据上；这是"用可重建性换吞吐"的经典权衡。
**后果**：
- 正面：导入安全 + 重算快。
- 负面：两套事务配置，容易误用；派生表在极端崩溃下可能不一致。
- 缓解：配置封装为 `unit_of_work(durability=DURABLE|REBUILDABLE)`，禁止裸调 `commit`；启动自检比对派生一致性，并支持"一键全量重建"。
**被否方案**：全库 FULL（重算慢 2~5 倍）；全库 NORMAL（导入可能丢数据，违反 RPO=0）。
**关联需求**：FR-L6、FR-R2/R3、NFR-4、NFR-5。

## ADR-0009 后复权 + as-of 因子快照

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD NFR-2/NFR-3 要求复权一致与时点一致；评审 F-B7 指出前复权价随未来除权变化会让历史指标不可复现，并与"可重放"直接冲突。
**决策**：收益率类一律使用**后复权（hfq）**或带 `factor_version` 的 as-of 因子快照；行情与财务数据全部落 `ledger_provenance`（source/fetched_at/as_of/checksum/quality_flags）；财务数据按 `announce_date ≤ 决策日` 过滤。
**理由**：
1. 后复权不随未来事件变化 → 历史结果可复现（NFR-5）。
2. as-of 快照让"上周的回撤"与"本周的回撤"基于同一因子版本。
3. PIT 过滤消除前视偏差（方向恒为正，加样本不能消除）。
**后果**：
- 正面：可复现、可审计、可对比。
- 负面：需要维护因子版本与快照存储；数据修正后需触发重算。
- 缓解：复权因子跳变告警（NFR-2）；`data_as_of` 进入 `MetricResult` 并在 UI 展示陈旧度；除权检测触发缓存失效。
**被否方案**：前复权实时计算（不可复现）；不复权（除权造成虚假极值，评审 F-A8 已点名）。
**关联需求**：FR-R4、FR-R5、NFR-2、NFR-3、NFR-5。

## ADR-0010 分层差异化覆盖率 + 变异测试

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD NFR-7 明确"100% 覆盖率不作为正确性判据"；但 v1.0 曾写"100% 单测覆盖"（评审 R-D8 已纠正）。同时口径错误代价极高。
**决策**：分层差异化目标——`core` 行/分支 100% + 变异分 ≥80%；`contracts` ≥95%；业务 domain ≥98%；application ≥95%；infra ≥85%；delivery ≥80%；整体 ≥90%/85%。并列四类"覆盖率抓不到"的测试：属性不变量、golden 复算、架构约束、变异。
**理由**：
1. 覆盖率高的代码仍可能"断言写得毫无意义"，变异测试才能证明断言有效。
2. 对 I/O 密集层追求 100% 是成本黑洞、收益极低。
3. core 是错误代价最高的层，值得最严格的成本投入。
**后果**：
- 正面：质量投入与风险对齐；口径层真正可信。
- 负面：变异测试慢，只能 nightly；分层门禁增加 CI 复杂度。
- 缓解：变异只跑 `core`；PR 走 fast lane（<60s）+ full lane；nightly 跑变异与属性大样本。
**被否方案**：全局 100% 覆盖（浪费时间且鼓励无意义断言）；只看覆盖率不做变异（断言质量无保障）。
**关联需求**：NFR-7、NFR-11、FR-R2~R8。

## ADR-0011 降级矩阵 + 引擎级门禁状态机

**状态**：采纳 ｜ 2026-10-19
**背景**：Review §3 R-C4 裁决"对账 FAIL 分级阻断 + 用户可见"；PRD FR-L6 要求资产类硬阻断、回合级标可疑；FR-R8 要求样本不足不出结论。若靠 UI 文案或开发者自觉，必然出现"某天某卡片悄悄显示了不该显示的数字"。
**决策**：把"结论安全性"做成**结构约束**——`MetricResult.status ∈ {ok, stale, blocked, unreliable}` 与 `sample_status ∈ {ok, insufficient, pending_window, blocked}` 由引擎计算；模板守卫在 `status != ok` 时**只能**渲染占位 + 原因 + 怎么办，物理上无法渲染结论。
**理由**：
1. 这是"会误导投资决策"的高危路径，必须结构性防呆而非流程约束。
2. 同一状态机同时服务：对账阻断、数据陈旧、样本不足、观察窗口未走完四类场景。
3. 降级矩阵（Reliability §7）可机械推导：状态 → 功能可用性。
**后果**：
- 正面：安全默认、可测试（快照断言阻断态）、跨出口一致（页面/报告/对话同源）。
- 负面：状态组合增多，模板分支复杂。
- 缓解：状态机集中定义 + 真值表测试 + 穷举状态快照。
**被否方案**：UI 层判断（易漏、不可测）；仅靠流程规范（无法保证）。
**关联需求**：FR-L6、FR-R8、FR-D1、FR-D2、FR-D3、NFR-4。

## ADR-0012 LLM 作为旁路、金额本地填充

**状态**：采纳 ｜ 2026-10-19
**背景**：PRD FR-D7.3 与 NFR-1 要求金额不出本机；但 v1.0 的"隐私闸门剥离金额"与 G3"我本月为什么亏"自相矛盾（评审 R-C7）。同时 LLM 幻觉在投资场景不可接受。
**决策**：金额与账号**由本地工具计算后填入回答模板**，LLM 只负责组织语言与解释；`EgressGuard` 在发送前断言不含金额/账号/股东代码；LLM 不可用或断网时，直接返回结构化结论 + 模板文案。
**理由**：
1. 同时满足隐私（不传金额）与体验（AI 知道你在说什么）。
2. LLM 退化不影响正确性，只影响措辞灵活度。
3. 出站断言可测试（安全是断言而非承诺）。
**后果**：
- 正面：隐私强保证、可用性强（断网可答）、幻觉影响面被压缩到"措辞"。
- 负面：回答灵活度受限；模板维护有成本。
- 缓解：模板库 + 固定问题按钮覆盖 80% 场景；自由输入走模板组合。
**被否方案**：LLM 直连数据库/传金额（违反 NFR-1，且无法审计）；完全不做 LLM（无法满足 FR-D7）。
**关联需求**：FR-D7、NFR-1、G4、C7。
