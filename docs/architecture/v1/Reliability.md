# 高可用与可靠性设计（Reliability）

> 版本 **v1.0** ｜ 2026-10-19 ｜ 上游：[PRD v1.1](../../prd/PRD-v1.md)（§4.2/4.3 部署形态、FR-L6 分级对账、FR-L7 数据主权、NFR-2/3/4/5/10/12）、[评审报告](../../prd/Review.md)（§3 R-C4 裁决、§7 里程碑）
> 形态：单进程 + SQLite 单文件 + 双击启动（FR-L1）；PG 仅可选 profile，复用本文机制，差异在各节标注。文中 ⚠ 数字为假设，须在 M0 用实测替换后才可写入验收。
> 结论：**本产品的"高可用"不是机器不宕机，而是「每次打开都能算对 × 每次崩了都能自愈 × 数据永远不会只剩一份」。**

## 1. 可用性重新定义

本产品没有"服务在线率"：一次使用 = 双击 → 打开页面 → 读数字 → 关掉。因此可用性是 `P(启动成功) × P(会话不中断) × P(数字可信)`——**渲染出错数字等于不可用**（与 R-C1 口径门禁一致）。

### 1.1 SLO 表
| SLO | 指标 | 目标值 | 度量口径 | 违反后果 |
|---|---|---|---|---|
| SLO-1 | 启动成功率 | ≥99.5%（M1）；M0 ≥99% | 双击到首屏可交互且 `doctor=PASS` 记成功，写 `sys_startup_log`；30 天滚动 | 冻结发版；每例失败必须归因到 §6 某检查项 |
| SLO-2 | 会话无崩溃率 | ≥99.5%（⚠ 150 次会话/年 ≈ 每年 ≤0.75 次） | 一次启动到退出 = 1 session；崩溃 = 非计划退出且 dirty 标记未清 | 同上；须产出 `logs/crash-<ts>.log` + 诊断包 |
| SLO-3 | 已提交数据持久性 | **RPO = 0**（`COMMIT` 返回即不丢） | FI-01/02 后比对已提交行数 | **不可接受 → 阻断发版** |
| SLO-4 | 备份 RPO / 恢复 RTO | 备份 ≤7 天（可配 1~30，宽限 10）；恢复 ≤5 分钟；季度演练通过率 100% | 备份成功时刻 → 还原后首屏可交互 + `doctor=PASS` 的墙钟时间 | 升级 P0；doctor 黄条 + 页面红字 + 月报脚注三重提示 |
| SLO-5 | 降级可用性 | 断网/行情故障且缓存 ≤T-1：回合、行为、看板、月报 100% 可用；净值/选股/择时部分可用且 **stale 标注率 100%** | 按 §7 逐格注入判定；标注率 = 带陈旧标签格子 / 应标注格子 | 矩阵与代码不一致视为 P0 口径缺陷 |
| SLO-6 | 可恢复性 | 崩溃后启动至一致状态 ≤5s（P95），**0 人工步骤**；全量重算终态 diff = 0 | kill -9 ×20 计时；重算后 golden fixture 比对 | P1；连续两次未达标则重排里程碑 |

> 三子是乘法关系：`99.5% × 99.5% × 数字可信 ≈ 99%`。这就是"界面先行 + 口径门禁必须并行"（R-C1）的量化理由——只修启动不修口径，可用性上限仍是 0。

### 1.2 RPO / RTO 分解
| 对象 | RPO | RTO | 达成机制 | 剩余不可控 |
|---|---|---|---|---|
| 已提交流水/指标（`review.db`） | 0 | ≤5s（全自动） | WAL + `synchronous=FULL` + 批次单事务（§3） | 断电时 SSD 写缓存谎报 flush（无 UPS，FM-02） |
| 未提交导入批次 | 整批回滚（无"半批"，等价 RPO=0） | 重导 ≤1 分钟 | 批次单事务 + `dedupe_key` 幂等 | — |
| 备份副本 | ≤7 天 | ≤5 分钟（⚠ 500MB 实测假设） | `sqlite3` backup API + 5 项校验 + 季度演练（§10） | 备份与库同盘且不云同步 → 磁盘坏即全失 |

### 1.3 明确不做的 HA（及理由）
| 不做 | 为什么在"单用户 + 单机 + 零安装"上是错的 | 替代 |
|---|---|---|
| 多活 / 主从 / 故障转移 / 负载均衡 | 用户只有一台电脑，第二副本没有承载者；5 万行、单写者，一台机器远超 NFR-10 预算 | 备份 + 迁移（FR-L7）：换机器 = "恢复"而非"切换" |
| K8s / 编排 / 灰度 / 蓝绿 | 与"双击启动、零安装"（§4.3）直接冲突；升级即原地替换 | 双击脚本 + 单例锁；迁移前自动快照可回退 |
| 消息中间件 / Redis / 外部缓存 | 单进程内无跨进程投递需求，多装一个服务就多一个启动失败点；缓存语义由 L1+L2 覆盖 | `EventBus` 进程内发布订阅 + `sys_job_run` 持久化作业 + §8 三层缓存 |
| 分布式锁 / ZooKeeper | 单机 `flock` + DB 部分唯一索引即可，且随进程消亡自动释放 | §5.4 两把锁 + 心跳 |
| 7×24 在线 / 监控告警平台 | 产品是"周五晚打开"，计划停机零成本；个人用户不看 dashboard，告警必须出现在他打开的页面 | 维护窗口随时可用；页面降级条 + 自诊断包（§11） |
| 异地容灾 / 双机房 | 没有第二个机房 | 备份目录指向 iCloud/Dropbox/OneDrive 即异机（§10.5） |

## 2. 故障模式与影响分析（FMEA）

> 基调：**任何故障都不得静默**（NFR-4/NFR-12）。"影响面"只写用户可感知后果；"残留风险"诚实保留。

| ID | 故障模式 | 检测手段 | 影响面 | 缓解（预防） | 恢复动作 | 残留风险 |
|---|---|---|---|---|---|---|
| FM-01 | 进程被 `kill -9`（强退/OOM） | 启动时 `.instance.lock` 持有者已死；无正常退出记录 | 未提交事务整批丢弃；`RUNNING` 作业悬空；`.tmp` 残留 | 写操作全在显式事务内；不在内存持有跨事务状态；30s heartbeat | §5.3 启动恢复：`RUNNING→INTERRUPTED`，有 checkpoint 续跑，否则标失败可重试 | 只丢当次未完成文件，由 GC 清理 |
| FM-02 | 断电 | 重启 `quick_check` + WAL 恢复日志；dirty 标记 | 已 `COMMIT` 不丢；未提交整批回滚 | WAL + `synchronous=FULL` + 批次单事务 | 自动回放/截断 WAL；doctor 报"上次非正常退出，已恢复" | SSD 写缓存谎报 flush（无 UPS），软件层无法消除 |
| FM-03 | 磁盘写满 | 作业前预检 `free < max(5GB, 2×db)`；捕获 `SQLITE_FULL`/`ENOSPC` | 导入、指标落库、备份、tmp 写全失败 | 预检门禁；日志 14 天/200MB 轮转；备份份数上限；cache 可清 | 清 `.tmp`/旧备份/parquet 冷数据，提示所需空间后重跑 | 分区满到连 rename 都失败时清理动作本身失败 |
| FM-04 | DB 文件损坏（坏块/同步盘/误操作） | 启动 `quick_check`；每周后台 `integrity_check` | 无法启动或数据不可读 | 禁止活库放同步盘（D-08 阻止启动）；archive 留原件 | 从最近备份还原 → 用 archive 原件按批次重导补齐增量 | 备份间增量（≤7 天）需重导；原件也丢则不可恢复 |
| FM-05 | `database is locked` | 捕获 `OperationalError` 计数 | 页面 500、作业失败、用户看"转圈" | 单写者队列（§3.2）；`BEGIN IMMEDIATE`；`busy_timeout=5000` | 自动重试 3 次（1/2/4s）；仍失败提示"数据库正忙，请 10 秒后重试" | 外部工具长写锁只能靠用户关闭 |
| FM-06 | Alembic 迁移失败 | 启动捕获异常；`sys_schema_version` 与期望不一致 | 应用无法启动 | 迁移前自动快照（`pre_migrate`）；迁移单事务；大表重建拆步 | 自动回滚快照并恢复旧版本，页面提示"升级未完成，已还原" | SQLite 大表 `ALTER` 需重建，>30s 期间断电靠备份 |
| FM-07 | 行情源超时 / 限频（429） | 超时计数、熔断状态、`mkt_fetch_log.http_status` | 指标 pending、页面 stale；**不阻塞导入** | 超时 3s/8s；退避+抖动；令牌桶；缓存优先；AlphaFeed 灾备 | 重试 → 降级缓存 → 换源；仍失败标 `pending_window` | 陈旧数据被当成实时（依赖 stale 标签显眼） |
| FM-08 | 行情源脏数据（字段漂移/涨跌停越界/复权不一致） | NFR-2 校验层：OHLC、涨跌停、振幅、日期越界、重复行、因子跳变 | 收益/回撤算错且"看起来正常" | 校验不过**不入计算**，落 `mkt_quarantine`；`factor_version` 登记 | 换源重拉；仍脏则标 stale 并剔除该标的（记录 N 与原因） | 语义漂移但校验能过 → 靠 golden fixture 回归 |
| FM-09 | LLM 超时 / 限流 / 返回非法 JSON | 连接 15s/总 30s 超时、429、Pydantic schema 校验失败 | 自由问答不可用；金额类仍可本地作答 | 固定问题模板本地渲染；数字本地填充（R-C7）；槽位化输出 | 重试 → 回退"本地结论+模板措辞"，底部标"未使用 AI" | 措辞不准，但数字结构上不可编造 |
| FM-10 | 备份盘不可用（未挂载/只读/权限） | `BackupTarget.probe()` 写探测；挂载点 inode 变化 | 备份失败（数据持久性降级，非功能不可用） | 每次备份前探测；失败重试 3 次跨 24h；降级写本地 `backups/` | 页面黄条"备份已失败 N 天"；换目录；恢复后自动补做 | 用户长期忽略黄条 → RPO 实际 >7 天 |
| FM-11 | 备份文件损坏 | 备份后立即校验：可打开+`integrity_check`+行数+sha256+指标 diff | 恢复时才发现不可用 → RTO 违约 | 备份后立刻验证，失败重做并保留上一份；manifest 记 sha256 | 回退上一份已验证备份；两份皆坏用 archive 重导 | 两份同时坏（低概率）；只留 1 份即单点 |
| FM-12 | 时钟跳变（NTP 回拨/手改） | `Clock` 双时间戳；运行中 wall 回拨 >60s 告警 | 调度重复/漏触发、TTL 误判、日志时序错乱、交易日归属错 | duration 全用 monotonic；日期归一无条件 UTC+8；作业幂等 | 暂停调度 → 重算触发时间 → 恢复；`misfire_grace_time` 补跑 | 跨日回拨可能重算两次（幂等无害，仅耗时） |
| FM-13 | 长时间指标重算被中断 | `RUNNING` + 陈旧 heartbeat | 部分窗口已提交，页面数字新旧混杂 | 按交易日窗口分批提交；checkpoint 与数据同事务；单飞锁 | 续跑只算**未完成窗口**；输入指纹变化则全量重算 | 跨版本中断需全量重算（更慢但正确） |
| FM-14 | 报告生成中途崩溃 | `report_index.status=GENERATING` + 文件不存在 | 报告打不开 / 半截文件 | 只允许 `tmp+rename` 落盘；文件就位后才写 DB 记录（§4） | GC 清 `.tmp`；状态改 `FAILED`；用户点【重新生成】 | 需重生成一次（≤1 分钟），数据无损 |
| FM-15 | 导入中断（大文件/关页/断电） | `import_batch` 无完成记录 | 该批判定不存在（整批回滚），不会半批 | 批次单事务；`dedupe_key` bag 幂等（A27） | 重导同一文件：已成功批次 0 新增，失败批次全量插入 | 5 万行单事务使 WAL 临时增长数十 MB |
| FM-16 | 并发双击启动两个实例 | 端口 `EADDRINUSE` + `.instance.lock` 被持有 | 双写 → SQLITE_BUSY；双调度 → 重复作业 | 单例 `flock`（进程死自动释放）；第二个实例只开浏览器后退出 | 自动，无人工步骤 | 用户删锁文件 → 端口 bind 兜底 |
| FM-17 | 系统休眠唤醒 | 唤醒后 wall−monotonic 漂移；调度 misfire | 定时作业错过；句柄/连接失效 | `misfire_grace_time=3600s` 补跑；唤醒触发连接健康检查 | 自动补跑错过作业并重建连接 | 睡眠期间不工作需在设置页说明 |
| FM-18 | 文件被误删（db/备份/cache/config） | doctor 检查关键路径与份数 | 丢库=全丢；删 cache=可重建；删 config=回默认 | 备份保留 N 份；设置页【打开数据目录】让删除有意识 | 备份还原；cache 自动重拉；config 重建默认 | 删整个数据目录且无外部备份 → 不可恢复（须提前告知） |
| FM-19 | 用户换机器 / 迁移 | 数据目录为空或机器指纹变化；manifest 不匹配 | 新机器没数据，误以为丢数据 | FR-L7 导出 + 备份目录可直接指向（恢复向导） | 【从备份恢复】→ doctor 校验 → 重建派生指标 → 首屏 | 平台差异（Windows 权限、macOS 沙箱）写失败 |

## 3. 崩溃一致性与存储层机制

> 这些参数不是性能调优，而是 SLO-3（RPO=0）的实现载体；每项都回答"单机下是否真的有用"。

### 3.1 参数与取舍
| 参数 | 取值 | 为什么这样选 | 代价 / 约束 | 单机真的有用吗 |
|---|---|---|---|---|
| `journal_mode` | `WAL` | 读写并发（页面可读时后台重算可写）；崩溃只需回放 WAL | 多 `-wal`/`-shm`；**不支持网络盘/同步盘**（D-08 检测） | 有用：NFR-10 下首页 3s 与后台写入并存 |
| `synchronous` | `FULL`（写连接） | RPO=0；`NORMAL` 在 WAL 下断电会丢最后若干提交 | 每次 commit 多一次 fsync（SSD ≈1~5ms），用批次化提交摊薄 | 有用：本地机器断电是真实故障，且无副本可补 |
| `busy_timeout` | `5000ms` | 单写者队列已消化竞争，此处只兜底读连接与外部工具 | 极端时用户等 5s 才见报错 | 有用：把"偶发 500"变成可预期等待 |
| `foreign_keys` | `ON`（每连接 PRAGMA） | 早失败：孤儿行写入即报错，而非指标算错后才发现 | 每连接必须设置（不持久化）；批量导入需按父子序 | 有用：派生表引用 `trade_id` 防脏引用 |
| `wal_autocheckpoint` | `1000` 页（≈4MB） | 太小导致 checkpoint 抖动，`0` 让 WAL 无限增长 | 大事务后有数十 ms 停顿 | 有用：把 WAL 峰值锁在可控范围（D-04 亦检测） |
| `cache_size` | `-32000`（32MB） | 500MB 库上提升重算与页面命中率 | 常驻 32MB 内存 | 有用：全量重算 ≤60s 的主要变量 |
| 写事务起始 | `BEGIN IMMEDIATE` | 直接拿写锁，避免"读后升级写"触发不可重试的 BUSY | 事务一开始即独占写 | 有用：死锁类错误从"偶发"变"没有" |

### 3.2 单写者队列（消除 `database is locked`）
| 机制 | 实现 | 为什么（单机有效性） |
|---|---|---|
| 单写连接 | `packages/platform` 一个专用写连接 + 单 worker（asyncio 队列，上限 64，满则返回"系统繁忙"）；所有写路径经 `TradeRepository`/`RoundRepository`/`NavRepository`/`MetricRepository`/`ReportRepository`/`JournalRepository` 端口汇入 | SQLite 本质单写者：并发写改成排队，锁冲突从随机变确定；写吞吐实测 <10 txn/s，64 足够 |
| 读连接池 | N 个只读连接（WAL 允许读不阻塞写） | 页面查询与重算写并行，保 NFR-10 的 3s |
| 顺序与例外 | FIFO：导入提交先于派生重算；备份串行走写连接；**恢复必须独占**（持单例锁，禁止任何写） | 避免"读到算了一半的新数据"；恢复期间的写会破坏一致性 |

### 3.3 事务边界
| 场景 | 事务边界 | 提交粒度 | 崩溃后语义 | 幂等键 |
|---|---|---|---|---|
| 账单导入 | 整文件：流水 + `import_batch` + 对账结果 + 隔离区 | 1 批 1 次 | 整批回滚，无半批 | `dedupe_key` bag（A27） |
| 批次撤销 | 该批 inserted 行软删 + `revoked_at` | 1 批 1 次 | 要么撤销要么没撤销 | `batch_id` |
| 日增量指标 | 每交易日：当日派生行 + 当日 checkpoint | 1 日 1 次 | 已提交日保留，未提交日重算 | `(metric_id, date, definition_version)` |
| 全量重算 | 按窗口（1 交易日/1 自然月）分批 | 1 窗口 1 次 | 从 checkpoint 之后续跑 | 先删窗口再插入（同事务） |
| 报告/备份元数据 | DB 记录在**文件 rename 完成后**写入 | 1 份 1 次 | 孤儿文件可 GC，绝不出现"有记录没文件" | `(kind, period)` / `(target, started_at)` |

### 3.4 幂等重放语义
| 层 | 语义 | 判据 |
|---|---|---|
| 导入 | 行级幂等：同 `dedupe_key` 按出现次数（bag）比对，只插入差额 | 重复上传同一文件新增 = 0（FR-L3 验收） |
| 派生指标 | 窗口级重放：`DELETE WHERE window` + `INSERT` 同事务，结果只取决于输入 | 同输入重算 `diff = 0`（NFR-5） |
| 作业 | checkpoint 提交边界 == 数据提交边界 | 续跑不重复算已完成窗口；重复也无害 |
| 文件副作用 / 事件 | `tmp → rename` 覆盖同名 + 渲染确定性；`EventBus` 至少一次投递 + 消费幂等 | 同输入两次 sha256 相同（时间戳进 manifest 白名单）；重复事件不产生重复派生行 |

> PG profile：`WAL/synchronous/busy_timeout/checkpoint` 由 PG 提供，仅 §3.1 换实现；§3.2 的单写者队列仍保留——它是业务串行化点，与数据库无关。

## 4. 原子性与文件写

对象：月报 HTML、Excel/JSON 导出、备份文件、parquet 归档、诊断包、manifest。统一走 `packages/platform` 的 `FileStore.write_atomic()` / `BackupTarget.save()`，**业务层禁止直接 `open(...,'w')`**（`contracts` 定端口契约，`core` 持有事务边界，`ledger` 管导入与对账，`review` 管派生指标，`delivery` 管报告与导出，`platform` 提供 FileStore/Clock/JobRunner/EventBus/BackupTarget）。

### 4.1 落盘步骤
```python
def write_atomic(path, chunks) -> ManifestEntry:
    tmp = path.with_name(f".{path.name}.{os.getpid()}.{uuid4().hex}.tmp")  # ① 同目录=同文件系统
    h, size = sha256(), 0
    with open(tmp, "wb") as f:
        for c in chunks: f.write(c); h.update(c); size += len(c)   # ② 流式写，峰值内存=1 chunk
        f.flush(); os.fsync(f.fileno())                            # ③ 数据落盘，断电不留空壳
    os.replace(tmp, path)                                          # ④ 原子改名：只见旧或新
    fsync_dir(path.parent)                                         # ⑤ 目录项落盘（POSIX；Win 退化为重试）
    return ManifestEntry(path, h.hexdigest(), size, now_utc())
```

| 约束 | 为什么 |
|---|---|
| tmp 必须在目标**同目录** | `rename` 跨文件系统非原子（`EXDEV`），会退化成拷贝 |
| 先 `fsync` 文件再 `rename` | 否则断电可能出现"文件名在、内容空/半"——比没有文件更糟 |
| 目标路径不可先删；DB 记录晚于文件就位；失败必删 tmp；启动 GC >24h | `replace` 本身覆盖；孤儿文件可 GC 而孤儿记录会让用户点开 404；残留 tmp 在磁盘满时持续吃空间 |

### 4.2 清单化校验（manifest.json，本身也原子写）
| 字段 | 含义 | 用途 |
|---|---|---|
| `files[].path/sha256/bytes/created_at` | 产物指纹 | 备份、恢复后逐文件比对 |
| `row_counts`（trades/rounds/nav_days/metrics） | 逻辑行数 | 抓"文件对但内容缺" |
| `schema_version` / `definition_version` / `manifest_sha256` | 版本与清单自身指纹 | 跨版本恢复判断是否需全量重算；防清单被改 |
| `key_metrics`（期末净值/TWR/费用合计） | 3 个哨兵指标 | 最快的端到端一致性检查 |

> 验收：恢复后 `manifest_ok=True` 且 `key_metrics diff=0`，与 FR-L7「导出→清空→导入 diff=0」同源判据。

## 5. 可恢复的执行模型

### 5.1 作业状态机（`sys_job_run`）
```
     APScheduler / HTTP → enqueue(kind, scope) ──取不到单飞锁──► 返回"已在运行"
               │
               ▼
         ┌─────────┐ 可重试异常且 attempt<3（退避 1s/4s/16s）──┐
         │ PENDING │◄──────────────────────────────────────────┘
         └────┬────┘
              ▼ 锁获取成功
         ┌─────────┐ 正常结束 ──► SUCCEEDED
         │ RUNNING │ 不可重试 / attempt≥3 ──► FAILED ──【重试】──► PENDING
         └────┬────┘
              ▼ 启动扫描发现 RUNNING
    INTERRUPTED ──checkpoint 有效且输入未变──► 回 RUNNING（续跑）
                └─无效/输入已变/连续中断 2 次──► FAILED
    安全点（窗口提交后）可取消 ──► CANCELED；终态三种：SUCCEEDED / FAILED / CANCELED
```

### 5.2 `checkpoint_json` 设计
| 字段 | 示例 | 语义 | 硬约束 |
|---|---|---|---|
| `v` | `1` | 结构版本 | 不兼容升级时旧 checkpoint 作废 |
| `kind`/`scope` | `metric.recompute`/`nav:daily` | 与单飞锁键一致 | 必须与 `sys_job_run` 列冗余一致 |
| `unit`/`cursor`/`done`/`total` | `trading_day`/`2025-06-30`/`812`/`2450` | 续跑单元与进度 | cursor 是**已提交**边界，不是已开始边界 |
| `input_fingerprint` | `sha256(trade_max_id, deleted_cnt, batch_max_id, factor_version)` | 输入是否变化 | 变化 ⇒ 作废 + 全量重算 |
| `definition_version` | `nav-v3` | 口径版本 | 变化 ⇒ 作废（否则新旧口径混算） |
| `attempt`/`last_error` | `2`/`MarketSourceTimeout` | 重试与诊断 | 只存 error_code + 摘要，不存 traceback |
| `heartbeat_at`/`heartbeat_mono` | wall + monotonic | 判定进程已死 | 双时间戳抗时钟跳变（FM-12）；整体 ≤64KB，不得含内存对象/句柄/大数组 |

### 5.3 启动时崩溃恢复（≤5s，0 人工）
| 步 | 动作 | 失败处理 |
|---|---|---|
| 1 | 非阻塞 `flock` 获取 `.instance.lock` | 已被持有 → 开浏览器后退出（FM-16） |
| 2 | 打开 DB（触发 WAL 恢复）→ `PRAGMA quick_check` → 写 `sys_startup_log(prev_dirty=true)` | 失败 → 进入恢复向导（FM-04）；写日志失败则内存态继续并报 doctor |
| 3 | `UPDATE sys_job_run SET status='INTERRUPTED' WHERE status='RUNNING'` | 无匹配 → 跳过 |
| 4 | 逐条判定：checkpoint 有效 ∧ 指纹匹配 ∧ heartbeat 陈旧 → 重新入队；否则 `FAILED` + `retry_hint` | 单条判定失败 → 标 FAILED，不阻塞启动 |
| 5 | GC `.tmp`（>24h）、清陈旧锁、刷新 doctor 快照、`EventBus.publish(recovery_completed)` | 任一失败 → WARN，不阻塞 |

> 为什么是"启动时扫描"而非"退出时写入"：`kill -9`/断电下退出钩子不执行，只有 DB 里的事实可信。这是单机可恢复性的唯一可靠锚点。

### 5.4 单飞锁 `(kind, scope)`
| 层 | 实现 | 覆盖的故障 | 为什么需要 |
|---|---|---|---|
| 进程内 | 按 `(kind, scope)` 分桶的 `asyncio.Lock` | 重复点击/重复入队 | 最便宜一层，覆盖 99% 场景 |
| 跨进程 | `.locks/{kind}.{scope}.lock` + 非阻塞 `flock`；`RUNNING` 行每 30s 心跳 | 双击两次、debug 会话、死进程残留 | 随进程消亡由内核释放，**无陈旧锁**（优于 pid 文件，pid 会复用）；心跳用于区分"真在跑"与"幽灵作业" |
| 数据库 | 部分唯一索引 `UNIQUE(kind,scope) WHERE status='RUNNING'` | 恢复路径、代码回归、绕过锁的调用 | 最后一道防线，让状态机自证 |

## 6. 启动自检与自愈（RTO 的关键）

`doctor` 每次启动串行执行（目标 ≤2s，`integrity_check` 移出首屏），结果落 `logs/doctor-<ts>.json` 并在设置页展示。结局三类：**自动修复**（继续启动）/ **降级**（继续启动 + 黄条）/ **阻止启动**（红字 + 恢复向导）。

| # | 检查项 | 失败阈值 | 自动动作 | 用户可见文案（NFR-12 三段式） |
|---|---|---|---|---|
| D-01 | DB 可打开 + 完整性（`quick_check`；后台周检 `integrity_check`） | 非 `ok` | 阻止启动 → 恢复向导（备份/重导） | 「数据文件打不开（可能损坏）。上面是最近 3 份备份，选一个恢复；原始账单在 archive/ 可重导。」 |

| D-05 | 磁盘余量 | `<max(5GB,2×db)` 黄条；`<1GB` 停止写入 | 只读模式：允许查看，禁止导入/备份 | 「磁盘只剩 800MB，导入会失败。请清理磁盘后重试；现在只能查看已有数据。」 |

| D-08 | 数据目录可写 / 非同步盘（写 `.probe`；匹配 iCloud/Dropbox/OneDrive/网络卷） | 不可写 / 命中同步盘 | 阻止启动 | 「数据目录在 iCloud 同步目录里，这样会损坏数据库。请改到本地磁盘「文档」下。」 |
| D-09 | 时钟、时区与脏退出（wall vs UTC+8；wall−monotonic；`.instance.lock`） | 回拨 >60s / 时区非 UTC+8 / 上次非正常退出 | WARN + 暂停调度 5 分钟待时钟稳定；脏退出 → 执行 §5.3 恢复 | 「系统时间似乎被调整过（偏差 2 小时），自动任务已暂停，请校准时间。」/「检测到上次非正常退出，已自动恢复（用时 1.8 秒）。」 |

## 8. 缓存与新鲜度

### 8.1 分层
| 层 | 位置 | 内容 | 生命周期 / 上限 | 单机有效性 |
|---|---|---|---|---|
| L1 内存 | 进程内 dict + TTL | 主数据、交易日历、当日快照、最近区间净值 | 进程存活期 / ≤256MB | 有用：首页 ≤3s 主要靠它（同 5 张卡片重复渲染） |
| L2 SQLite | `mkt_daily_bar`/`mkt_adj_factor`/`mkt_security_master`/`mkt_calendar` | 日线、复权因子、主数据、日历 | 持久可重建 / ⚠≤300MB | 有用：断网可用性与"重算不必重拉"都靠它 |
| L3 parquet | `cache/parquet/{table}/{year}.parquet` | 冷年份明细（>3 年）与灾备重建源 | 持久 / 按年切分 | 有边界：DB >200MB 后才引入，由 `cache_policy` 阈值控制 |

读取顺序 **L1 → L2 → L3 → 网络**：命中即返回，网络只补洞。这条顺序保证"网络不可用不会让已有数据消失"。

### 8.2 TTL、陈旧度与页面措辞（对应 PRD 附录 C 人话层）
| 数据 | 新鲜定义 | TTL | 陈旧处理 / 页面措辞 | 断网可用性 |
|---|---|---|---|---|
| 交易日历 | 覆盖到当年 12-31 | 1 年 | 阻止新区间诊断；「交易日历待更新，请联网一次」 | 只读可用（历史区间可算） |
| 日行情/复权因子 | 最近交易日 18:00 后视为 T 日新鲜 | 24h | `stale` + 截至日，当日净值用前收；「行情截至 2025-06-30（3 个交易日前）」，>10 日则收益类数字加删除线 | 可用（有缓存即算） |
| 基准指数 | 同行情 | 24h | `stale`，超额照出带基准截至日；「基准数据截至 X」 | 可用 |
| 财务/公告（PIT） | 按公告日增量 | 7 天 | `pending_window`，不进分母（NFR-3）；「观察期还没走完（暂不计入结论）」 | 可用（历史不变，PIT 快照天然离线友好） |
| 证券主数据 / 无风险利率 `rf` | 每周校验 | 7 天 | `stale`；「主数据/rf 为 7 天前」 | 可用 |
| 离线态 | 外网不可达 | — | 全局 `offline`；「当前离线，用的是本机缓存」 | 触发 SLO-5 判定 |

### 8.3 缓存失效：除权 / 复权因子跳变
| 触发 | 检测 | 动作 | 用户可见 |
|---|---|---|---|
| 除权除息日 `adj_factor` 跳变 | NFR-2：相邻日因子比 ≠1 且与公告日匹配 | `factor_version += 1`；重拉价格序列；`input_fingerprint` 变化 → 排重算 | 「检测到 3 只股票除权，历史收益已按后复权重算，数字可能略有变化。」 |
| 前复权漂移（若误用 qfq） | 一致性校验：hfq 与 qfq 收益率应一致（NFR-2） | 拒绝 qfq 入计算，只用 hfq / as-of 快照 | 「价格口径异常，已自动切换到后复权序列。」 |
| 因子缺失 | 窗口内 `adj_factor` 有空 | 该标的窗口 `pending_window`，不进比率分母 | 「2 只股票缺复权数据，本次已剔除（N 从 45 降到 43）。」 |

## 9. 数据源弹性

### 9.1 超时 / 重试 / 退避
| 参数 | 值 | 依据 |
|---|---|---|
| 行情连接/读超时 | 3s / 8s | akshare 为爬虫聚合，>8s 基本意味着源不可用 |
| LLM 连接/总超时（`LlmProvider`） | 15s / 30s | 单轮问答可接受上限，超时即降级模板；金额数字一律由 `ToolGateway` 本地计算 |
| 最大重试 / 退避 / 作业级重试 | 单请求 3 次、指数 `1s → 4s`、抖动 ±30%、4xx 不重试；整批失败回 `PENDING` 最多 3 次 | 覆盖瞬时抖动；抖动防同批标的齐步重试打爆源；作业级与单请求重试分离避免放大 |

### 9.2 熔断器
```
 CLOSED ──(60s 内失败 ≥5 次 且 失败率 >50%，样本 ≥10)──► OPEN
   ▲                                                     │ 冷却 60s，连续失败翻倍至 600s 上限
   └──探测成功(1 次)──────────────────────────── HALF_OPEN
              探测失败 ──────────────────────────► OPEN（冷却重置为当前值×2）
```
- OPEN 期间直接走缓存/灾备、不发请求；HALF_OPEN 只放 1 个探测（单机并发低）。
- 状态落盘 `sys_breaker(scope,state,opened_at,failures)`：重启后不立刻重试已熔断的源（否则冷启动打爆源）；设置页【重试行情源】供用户网络恢复后手动复位。

### 9.3 限频、降级顺序与部分失败
| 机制 | 实现 | 说明 |
|---|---|---|
| 令牌桶 + 批量化 | 容量 10、速率 1 req/s（⚠ 假设上限 60/min）；优先"全市场某日"批量接口再退化单标的 | 请求数从 O(标的×天) 降到 O(天) |
| 降级顺序 | **L2/L3 缓存 → akshare → AlphaFeed → 放弃并标 stale/pending** | 缓存优先：旧数据可解释（带日期），没数据不可解释 |
| 部分失败 ≤20% | `SUCCEEDED(partial)`：成功入库，失败标 `pending_window` 并从比率分母剔除 | 黄条：「3 只股票行情获取失败，本次已剔除（N=42）」 |
| 部分失败 >20% / 单标的校验失败 | `FAILED(MARKET_SOURCE_DEGRADED)` 本次不落库、保持旧缓存；单标的进 `mkt_quarantine` | 红字 + 【重试】；隔离区可查原因与原始行 |

> **绝不出现"部分成功但静默"**：任何剔除都必须落到 (a) 计数、(b) 页面标注、(c) `mkt_fetch_log` 留痕三处。

### 9.4 请求去重与 provenance（`mkt_fetch_log`）
| 字段 | 示例 | 用途 |
|---|---|---|
| `source`/`endpoint`/`symbol`/`params_hash` | `akshare`/`stock_zh_a_hist`/`300308`/`sha256(...)` | 定位哪个源出问题；同一请求在作业内只发一次（内存 dedupe map） |
| `fetched_at`/`latency_ms`/`http_status`/`rows`/`checksum`/`validation` | `612`/`sha256`/`ok / quarantine / reject` | 性能与可用性统计；NFR-2 拉取留痕，证明"异常不入计算" |
| `job_id`/`factor_version` | — | 与作业、口径版本关联，支撑 NFR-3/NFR-5 复现 |

## 10. 备份与恢复（RPO/RTO 落地）

### 10.1 策略表
| 类型 | 频率 / 触发 | 内容 | 保留 | 位置 | 为什么 |
|---|---|---|---|---|---|
| 自动全量 | 每周（默认周日 20:00，可配） | `review.db` + `archive/` 原件 + `config` + manifest | 8 份（≈2 个月） | 用户指定目录（默认 `backups/`，可指向云盘/移动硬盘） | ⚠500MB 全量仅数秒；**不做增量**：增量链断裂风险 > 容量收益 |
| 迁移/升级前快照 | Alembic 迁移前、用户点【立即备份】 | 同全量，`tag=pre_migrate/manual` | 3 份 | `pre_migrate/` 子目录 | 迁移失败是唯一"应用自己弄坏数据"的场景，必须可回退 |
| 年度冷归档（可选） | 每年 1 次 | parquet（行情）+ 原始账单 zip | 10 年 | 用户指定 | 换机器/长期保存的最小体积副本 |
| 导出（FR-L7 Excel+JSON） | 用户手动 | 逻辑全量 + 元数据 + `definition_version` | 用户自管 | 用户选择 | 面向"人读/跨版本/迁移"，不是恢复主路径（§10.4） |

> `cache/` 不备份（可重拉）；代价是恢复后断网没有行情缓存，取舍显式记录在此。

### 10.2 一致性备份方法
| 做法 | 判定 | 原因 |
|---|---|---|
| `sqlite3.Connection.backup()` / CLI `.backup` | ✅ 唯一允许 | 在线一致性快照：页级复制 + WAL 语义正确，拷贝期间可继续读 |
| `cp review.db backup.db` | ❌ 禁止 | WAL 中未 checkpoint 的事务不在主文件 → 备份缺最近提交，甚至页撕裂 |
| `zip`/`tar` 整个数据目录；在同步盘/网络盘直接备份活库 | ❌ 禁止 | `-wal`/`-shm` 与主文件不同步，恢复出半状态；云盘拿到撕裂文件 |

作业形态：`JobRunner(kind='backup', scope=target)` 单飞；备份期间写队列照常（backup API 允许），**恢复必须独占**（持单例锁）。

### 10.3 备份校验（5 项全过才算成功）
| # | 检查 | 通过判据 | 失败动作 |
|---|---|---|---|
| 1 | 可打开 | 连接 + `PRAGMA integrity_check == ok` | 重做一次；再失败保留上一份 + 红字 |
| 2 | 逻辑行数 | trades/rounds/nav_days/metrics 与源库一致（容差 0） | 同上 |
| 3 | 文件指纹 | sha256 与 `manifest.json` 一致 | 同上 |
| 4 | 哨兵指标 | 期末净值 / TWR / 费用合计 三项重算 diff = 0 | 同上 |
| 5 | 版本 | `schema_version`、`definition_version` 与源一致 | 标版本差异，恢复时强制全量重算 |

> 校验失败不删坏文件，改名 `*.bad-<ts>` 保留供诊断——否则用户永远不知道备份为什么失败。

### 10.4 恢复演练（每季度 restore drill）与导出关系
| 步 | 动作 | 通过判据 | 记录 |
|---|---|---|---|
| 1 | 备份复制到临时目录，`--data-dir` 指向它启动 | 启动成功且 `doctor=PASS` | `restore_seconds` |
| 2 | 对比行数 + 哨兵指标 | `manifest_ok=True`，3 项 diff = 0 | diff 明细 |
| 3 | 分层抽样 30 回合（对齐 PRD G1） | pnl 差额 ≤0.01 元、收益率 ≤1bp | 抽样清单 |
| 4 | 生成月报 + 导出 Excel/JSON | 文件可打开，数字与页面一致 | 产物路径 |
| 5 | 删掉工作库，用演练过的备份正式恢复；再断网启动一次 | 首屏可交互，总耗时 ≤5 分钟（SLO-4）；断网仍出回合/行为卡片 | `logs/restore-drill.jsonl` |

**导出 vs 备份**：备份是物理层（逐位一致、只能本应用恢复）；导出是逻辑层（人可读、跨版本、可作交叉验证）。恢复后**可选**用最近一次导出校验，但不作恢复主路径；两者都必须走 §4 原子写 + manifest。

### 10.5 3-2-1 在单机下的现实裁剪
| 原则 | 单机现实 | 我们的做法 |
|---|---|---|
| 3 份副本 | 工作库 + `backups/` 多份 + 年度归档 | 自动满足（保留 8 份） |
| 2 种介质 | 用户通常只有一块 SSD | doctor 检测备份目录是否与数据目录**同卷** → 同卷黄条：「备份和数据库在同一块磁盘上，磁盘坏了两份一起没」 |
| 1 份异地 | 没有第二台机器 | 建议把**备份目录**（静态文件）放进 iCloud/Dropbox/OneDrive；**严禁把活库放同步目录**（D-08 阻止启动） |

### 11.1 结构化日志字段（structlog → `logs/app-%Y%m%d.jsonl`）
| 字段 | 必填时机 | 示例 | 用途 |
|---|---|---|---|
| `ts_wall`/`ts_mono` | 全部 | ISO8601 UTC+8 / 单调纳秒 | 抗时钟跳变排序（FM-12） |
| `level`/`event` | 全部 | `info`/`import.batch_committed` | `event` 用稳定英文 snake_case，便于计数 |
| `request_id` | HTTP | ULID | 一次页面请求全链路串联 |
| `job_id`/`run_id` | 作业 | `sys_job_run.id` | 作业与数据变更对账 |
| `user_id` | 数据类 | `100000` | 单用户但保持分区一致（FR-L2） |
| `stage` | 业务阶段 | `import.parse`/`reconcile`/`metric.nav`/`report.render`/`backup.verify` | 定位"慢/错在哪一步" |
| `metric_id`/`definition_version` | 指标类 | `nav.twr`/`nav-v3` | NFR-4 可追溯 |
| `duration_ms` | 阶段结束 | `1840` | NFR-10 预算与 SLO 度量 |
| `outcome`/`error_code`/`rows_in`/`rows_quarantined` | 结束 / 导入 | `ok`/`SQLITE_FULL`/`328/3` | 错误分类只用枚举；导入质量趋势 |
| `source`/`data_as_of`/`stale`/`degrade_reason` | 行情相关 | `akshare`/`2025-06-30`/`true`/`market_timeout` | 与 §7 矩阵逐格对应 |

### 11.2 级别、脱敏、健康检查与指标
| 级别 | 用在哪 | 举例 | 默认 |
|---|---|---|---|
| ERROR | 用户可感知的失败 + 需动作 | 导入失败、DB 损坏、备份校验失败 | 开 |
| WARN | 降级、重试、校验拒绝、可疑数据 | 熔断 OPEN、标的被剔除、stale 超阈值 | 开 |
| INFO | 业务里程碑 | 批次提交、作业状态变更、启动/恢复、备份成功 | 开 |
| DEBUG | 逐行解析、SQL、HTTP 明细（诊断包内临时开 5 分钟） | 列映射过程 | 关 |

| 敏感项 | 处理 | 例外 |
|---|---|---|
| 股东账号 | 只留后 4 位（`****1469`） | 用户勾选"诊断包含账号"（默认关） |
| 金额 / 路径 / 出站 | 日志不写金额原值（只写 `amount_present` 或量级档）；家目录替换 `~`；断言测试出站不含金额与账号（FR-D7.3） | FR-L7 导出是明确动作，不受日志脱敏限制 |

| 端点 / 产物 | 内容 | 说明 |
|---|---|---|
| `GET /healthz` / `GET /readyz` | 进程存活；DB 可读、schema ok、最近 doctor、队列深度 | `/readyz` 供启动脚本决定是否开浏览器；两者都不泄露路径与金额 |
| `GET /diagnostics` → `diagnostics-<ts>.zip` | doctor JSON、最近 7 天脱敏日志、最近 50 条 `sys_job_run`、200 条 `mkt_fetch_log`、版本/OS/Python、备份清单 | 用户自留或发支持；本地生成，不经网络 |

**进程内指标**（`sys_metric_counter` 定期快照 + `GET /metrics` 本地 Prometheus 文本）：`import_rows_total` / `import_quarantine_ratio`（隔离率 >5% 连续 3 次 → WARN）、`reconcile_broken_total`（>0 即红字，FR-L6）、`job_duration_seconds{kind}`（全量重算 P95 >60s 违反 NFR-10）、`job_failures_total{kind}`、`degrade_events_total{reason}`（与 §7 逐项对齐，验证 SLO-5）、`market_fetch_latency` / `cache_hit_ratio`（<80% 复查缓存策略）、`backup_age_days` / `wal_size_bytes` / `db_size_bytes`（>7 天黄条，WAL >100MB 告警）。
**追踪**：默认 `logs/trace/<request_id>.jsonl`，埋 4 段 span（http → repo → market/tool → render），回答"首页 3s 花在哪"；OpenTelemetry 通过 `OTEL_ENABLED=1` 可选，**默认关闭**——单机没有 collector，开启只会让用户多装服务（同 §1.3 理由）。

## 12. 故障处置 Runbook

> 前提：用户是非程序员（PRD §3.1），**任何 SOP 第 1 步都必须是他能点到的按钮**；文案遵循 NFR-12 三段式。

| SOP | 症状 | 用户看到什么 | 三步处置 | 验证恢复 |
|---|---|---|---|---|
| SOP-1 启动后没打开/端口冲突 | 双击后无窗口或地址打不开 | 「应用已启动，但 8787 被其他程序占用，已改用 8788，[点这里打开]」 | ① 点页面给的链接；② 仍失败则关掉占用程序后重启；③ 再不行点【复制诊断包】 | 首页出现且无红条；`app-*.jsonl` 有 `start.ready` |
| SOP-2 启动卡在自检（库损坏/schema 不匹配） | 红字"数据文件打不开"或"版本比数据格式旧" | 恢复向导：列最近 3 份备份 + 各自日期与指标摘要 | ① 选最近备份【恢复】；② 提示"备份后有新账单"则用 archive 原件重导；③ 升级场景先【更新应用】 | `doctor=PASS`；数字与最近看板一致；`restore-drill.jsonl` 新增记录 |
| SOP-3 导入转圈 / "数据库正忙" | 进度条超过 30 秒不动；红字"数据库正忙" | 「正在等前一个任务结束（已 12 秒）」→ 超时后「请 10 秒后重试」 | ① 等 10 秒点【重试】；② 关闭 DB 浏览器等占锁工具；③ 重启应用（自动清锁与 tmp） | 导入结果页出现（新增/跳过/隔离）；重复上传 0 新增 |
| SOP-4 对账断链 / 净值不可用 | 红字「3 月 12 日前后余额对不上…本月收益暂不可信。[查看断点行]」 | 断点行号、期望与实际余额；资产类卡片显示"数据可疑"占位 | ① 点【查看断点行】判断是否漏导/漏一笔转账；② 补导该期间账单（修复模式/区间替换）；③ 重跑对账 | 红字消失；`reconcile_broken_total` 不再增长；抽样 3 回合余额链自洽 |
| SOP-5 备份连续失败 | 设置页红字「备份已失败 5 天」+ 首页黄条 | 探测结果（目录不存在/只读/空间不足）+【重新选择目录】【立即备份】 | ① 接移动硬盘或改本地 `backups/`；② 点【立即备份】；③ 成功后把该目录加入云盘同步（**只同步备份文件，不同步 review.db**） | `backup_age_days <1`；5 项校验全过；`sys_backup_log` 新增 success |
| SOP-6 指标重算中断/数字不一致 | 黄条「上次重算未完成，正在续跑」或卡片显示旧值 | 进度 N/M 窗口 + 预计剩余；失败时【重试】 | ① 等续跑（一般 <30s）；② 失败点【重试】（自动弃无效 checkpoint 全量重算）；③ 仍失败点【重建派生数据】（保留流水，只清派生表） | 进度 100%；与 golden 结果 diff=0；`job_duration_seconds` 落库 |
| SOP-7 行情拉取失败（stale/pending） | 卡片黄条「行情截至 3 个交易日前」；选股/择时"样本不足" | 失败标的数、熔断原因、缓存截至日 | ① 检查网络（源可能临时不可用，30 分钟后再试）；② 点【重试行情源】；③ 设置页切换 AlphaFeed 灾备源 | 黄条消失或退回 ≤1 日；`mkt_fetch_log` 最新 `validation=ok`；pending 标的数下降 |
| SOP-8 误删数据 / 换机器 | 首页空白或「还没有数据」；迁移后启动失败 | 恢复向导（从备份/从导出文件/从 archive 原件） | ① 设置页【从备份恢复】选最新备份；② 无备份则【从导出文件导入】（Excel+JSON）；③ 再不行用 `archive/` 原件按批次重导 | 行数/回合数与预期一致；D-06 显示备份新鲜；能生成月报 |

### 13.2 Soak test 与发布门禁
| 用例 | 规模 | 判据 |
|---|---|---|
| 连续导入 200 次 | 同文件反复导入 + 交错 10 个不同批次 + 每 20 次撤销一次 | 重复文件新增恒为 0；总行数符合期望；无滞留 `RUNNING`；WAL 峰值 <32MB；RSS 增长 <20% |

| 72 小时空闲 + 降级长跑 | 常驻；行情源持续不可用 24h | 无内存泄漏（RSS 斜率 ≈0）；无定时器堆积；日志 <200MB；持续标 stale，恢复后自动补齐且 diff=0 |

| 门禁 | 要求 | 里程碑 |
|---|---|---|

> **诚实边界**：本文机制能覆盖的残留风险只剩四类——SSD 谎报 flush 导致的极端断电丢已提交事务、备份与库同盘叠加磁盘损坏、用户长期忽略告警使备份实际停摆、行情源语义漂移而校验仍通过。前两类靠"周备份 + archive 原件重导"兜底，后两类靠"三重可见告警 + golden fixture 回归"兜底；不存在第四层保险，也不假装存在。
